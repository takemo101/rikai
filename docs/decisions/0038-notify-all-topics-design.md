# ADR-0038 F46（ほかのトピックの通知）の設計

- 日付：2026-11-24
- 種別：AI の設計の判断（もとは、SPEC.md の §8 の表の 1 行。文言は、そのまま移した）
- 関連の機能：[F46](../features/turn-notify.md#f46-ほかのトピックの新着も通知する)
- 決定の元：[利用者の決定](user-decisions.md)（2026-11-24「ほかのトピックの新着も通知する（進める）・要素の見た…」）。文中の「上の…」は、この決定を指す。
- 一覧：[ADR の一覧](README.md)・[SPEC.md の §8](../../SPEC.md#8-利用者の判断)

（AI の判断。上の決定の範囲。0.27.0）**F46 の設計**：

- (1) **`fresh` を、既存の一覧 API（`/api/topics`）に足した**：新しい経路を作らず、すでに、一覧のたびに `threads.json` を走査している `progress` と、**同じ 1 回の走査**で作れるため（`summaryOrNull`）。**`.rikai/` の保存の形は、変えない**・応答に省略できる項目を足すだけ（古い画面は無視できる）。結果は、`rev`・更新時刻・大きさをキーに覚える（変更のないトピックを、一覧のたびに、読み直さない）。
- (2) **上限を付けた**：各項目は新しい側から 200 個・応答全体で ID 合計 4000 個（超えたトピックには `fresh` を付けない）：一覧の応答が、トピックの数・履歴の長さで、際限なく大きくならないため。**代償：上限を超えたトピックの新着は、静かに洩れる**（通知されない）。許容した（実際の使い方では、200 個を超える新着が、一度に届くことは、まれ：推測）。**`openAsks` は、切ったあとの `asks` の部分集合**にした（窓の外の古い質問が、毎回、新着に見えないように）。閉じたトピックには付けない（新着がない）。
- (3) **新着の判定（`freshOf`・`awaitsAnswer` など）は、`shared/fresh.ts` の 1 か所**に移した：サーバーの `fresh` と、画面の、開いているトピックの `snapshotOf` が、**同じ関数**を使う（2 通りの判定が、食い違わないように）。
- (4) **開いているトピックは、一覧の経路から除く**：開いているトピックは、取得した全体から通知する（これまでどおり）。一覧の `fresh` からも通知すると、**二重に通知する**ため。開いているかは、トピックのクエリを見ているか〔observer がいるか〕で決める。
- (5) **ベースラインの規則**：最初の一覧・つながり直し・一覧に新しく現れたトピック・**取得元が、一覧からトピックに変わったとき**（一覧の `fresh` は、新しい側の窓だけなので、トピックの全体とは、直接、比べられない：比べると、窓の外の古い ID が、新着に見える）。前回の状態は、取得元つきで、共有の `last` に持つ。
- (6) **開き直した直後は、開く直前に届いた返信を、通知しない**：開いた時点で、画面に見えているため。
- (7) **`styles` の値の上限を、80 → 300 文字にした**：`font-family` など、長い値が、切れて、読めなかったため（利用者の決定）。20 個 × 300 字 = 約 6KB で、`frameMeta` 全体の 16KB に収まるので、他の上限は変えない。橋のスクリプトも、同じ定数（`STYLE_VALUE_MAX`）で切る。
- (8) **SKILL.md は変更なし**：AI への指示は、変わらない（通知は、画面の機能）（[検証記録](../verification.md)）
