# ADR-0016 画面の更新を SSE にした

- 日付：2026-11-23
- 種別：AI の設計の判断（もとは、SPEC.md の §8 の表の 1 行。文言は、そのまま移した）
- 関連の機能：[F38](../features/turn-notify.md#f38-画面の更新はサーバーの通知で届く)
- 決定の元：[利用者の決定](user-decisions.md)（2026-11-23「画面の更新を、ポーリングから SSE に切り替える（…」）。文中の「上の…」は、この決定を指す。
- 一覧：[ADR の一覧](README.md)・[SPEC.md の §8](../../SPEC.md#8-利用者の判断)

（AI の判断。上の依頼の範囲。0.19.0）**画面の更新を、SSE にした**（F38）：**通知だけ push する**（データは、既存の取得で取る：HTTP の他の経路・形式は、変えない）。**ポーリングは、保険として残す**（つながっている間は止め、切れたら 1.5 秒に戻す）。**検知は、`fs.watch`（再帰）と、約 300ms の確認の併用**（`rikai apply` は、CLI の別のプロセスが書くので、サーバーは、ファイルを見る）。**購読者がいる間だけ**動かす。**認証は、既存の `/api/*` の検査**（N1・N2 に影響しない）。**設計案にない追加**：通知で起きた取り直しが失敗したら、つながっていても、ポーリングに戻る（既存の e2e が必要とした）。**CLI は、変えない**。§5 の「サーバー側から押し出さない」は、「データごと押し出さない」に変えた。**独立レビューの Blocker（タブ 6 つで、全タブが止まる）への対応として、接続を `SharedWorker` で、ブラウザ全体で 1 本にした**：Web Locks ＋ `BroadcastChannel` のリーダー選出は、リーダーのタブが背景で凍結されると、フォロワーが「つながっている」と思ったまま更新が止まるため採らず、タブの凍結の影響を受けない `SharedWorker` を採った。**`SharedWorker` がない環境は、タブごとの `EventSource` にフォールバックせず、ポーリングだけ**（6 タブの枠の枯渇を避けるため）。同時接続 20 は、保険として残す（ブラウザ全体で 1 本になったので、通常は効かない）。つながっていたものが切れた 1 回だけ、すぐ全体を取り直す。**実測**：`apply` 開始 → 画面 中央値 736ms → 125ms・定期の GET（60 秒）80 回 → 0 回（[検証記録](../verification.md)）
