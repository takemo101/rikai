# ADR-0039 一覧の fresh の上限

- 日付：2026-11-24
- 種別：AI の設計の判断（もとは、SPEC.md の §8 の表の 1 行。文言は、そのまま移した）
- 関連の機能：[F46](../features/turn-notify.md#f46-ほかのトピックの新着も通知する)
- 決定の元：[利用者の決定](user-decisions.md)（2026-11-24「ほかのトピックの新着も通知する（進める）・要素の見た…」）。文中の「上の…」は、この決定を指す。
- 一覧：[ADR の一覧](README.md)・[SPEC.md の §8](../../SPEC.md#8-利用者の判断)

（AI の判断。F46 の独立レビューの指摘への対応。0.27.0）**一覧の `fresh` の上限を、「応答全体で ID 合計 4000 個を超えたトピックには付けない」から、「窓を、通知の対象のトピックの数で割り、全トピックに同じ窓で付ける」方式に変えた**：前の方式は、20 トピック × 各 200 件で、一覧の順で**後ろのトピックが、静かに、通知の対象から外れ**、何が来ても通知されなかった（外れたことが、画面にも、利用者にも、分からない）。窓を割れば、全トピックに付き、1 トピックあたりの窓が、小さくなるだけ（`clamp(floor(4000 / N), 20, 200)`）。**下限 20 を置いた**：窓が 0 に近づくと、新着の判定ができないため。**代償**：窓は、各項目の上限で、1 トピックに最大 4 項目あるので、ID の合計は、最大で約 4 倍（最悪 16000 個）になる。許容した。**対象が 200 を超えるときだけ、予算を超える**：更新が新しい順に 200 個に付ける（更新の古いトピックは、通知されない：既知の制約）。**窓の大きさを、応答に含める（`fresh.window`）**：窓は、トピックの増減で変わり、窓の境目で、古い ID が「新着」に見えうる。画面が、窓の変化を、**確実に**検出するため（推測や、別の値からの逆算に、頼らない）。**窓が広がったとき**（古い ID が窓に新しく入る）は、そのトピックを**ベースライン**にする（新着に見えないように）。窓が縮むときは、古い ID が窓から消えるだけなので、そのまま比べる。**その代償：窓が広がった瞬間に届いた新着は、ベースラインに吸収され、通知されない**（窓が変わるのは、トピックの増減のときだけなので、許容した）。**キャッシュのキーに、窓を加えた**（窓が違えば、別の結果）。**一度に窓以上の新着が届くと、「返信 200 以上」と出す**（`capped`）：件数が窓で切れているのに、正確な数に見えて、誤解させないため。**直さなかった**：新しいページが「新しい版」として数えられる（F41 の数え方のまま。別の判断）・トピックを消しても、記録が残る（トピックの数だけで、小さい）（[検証記録](../verification.md)）
