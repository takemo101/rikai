### F38 画面の更新はサーバーの通知で届く

**画面の更新は、サーバーの通知（SSE）で届く**（利用者の依頼：2026-11-23。「画面の更新を、ポーリング〔1.5 秒ごと〕から SSE に切り替える」。設計案への回答：「この案で進める」〔通知だけ push・ポーリングは保険で残す〕）：

- (1) **経路 `GET /api/events`**（`text/event-stream`。`Cache-Control: no-store`・`X-Content-Type-Options: nosniff`・圧縮なし）。**認証は、既存の `/api/*` の検査をそのまま**（合言葉なし・不正な Host・不正な Origin は 403。既存と同じ文言。`EventSource` は、同じオリジンの Cookie を送る）。**同時接続は 20 まで**（超えたら 503。画面の接続はブラウザ全体で 1 本になったので、通常は効かない保険）。CSP の `connect-src 'self'` で許される。
- (2) **イベント**：**データは送らず、「変わった」という通知だけ**：`event: ready`（つながった直後・再接続のあと）・`event: changed`（`data` は `{"topics":true}`〔一覧の変化〕か `{"slug":"…","rev":N}`〔そのトピックの `rev`〕。`shared/api.ts` の `changedEvent`）・15 秒ごとに `: ping`（コメント行）。
- (3) **検知**：`rikai apply` は、CLI の別のプロセスが `.rikai/` を直接書き、画面を配るサーバーは別のプロセスなので、サーバーは、**ファイルの変更を見る**：**購読者が 1 人以上いる間だけ**、`fs.watch`（再帰）と、**約 300ms ごとの確認**（`stat` の印が変わったトピックの `meta.json` から `rev` を読む。`fs.watch` の取りこぼし・OS の差への保険）を動かす。0 人になれば、ウォッチャーもタイマーも解く。連続した変化は 30ms にまとめ、`rev` が変わったときだけ通知する。トピックの新規・消えるは `{topics:true}`。`fs.watch` の `'error'` は、プロセスを落とさず、確認だけで続ける。
- (4) **画面**：**SSE の接続は、ブラウザ全体で 1 本**。`SharedWorker`（`web/api/eventsWorker.ts`。名前 `rikai-events`）が `EventSource('/api/events')` を 1 本だけ持ち、`ready`・`changed`・`error` を、開いている全タブへ配る（新しいタブには、いまの状態を返す。タブの `pagehide`・アンマウントで `bye` を送り、0 タブになったら閉じる）。**理由**：Chrome は HTTP/1.1 で 1 オリジンの接続を 6 本までしか開かず（タブ・窓をまたいで共有）、タブごとに SSE を持つと、6 タブで枠が埋まり、全タブの操作・取得が止まる。**`SharedWorker` がない環境は、SSE を使わず、ポーリングだけ**（タブごとの `EventSource` には、フォールバックしない）。通知を受けたら、既存の取得（トピックは、持っている `rev` と同じなら取り直さない・一覧は取り直す）を、すぐ実行する。`ready` では、全体を取り直す。**つながっている間は、ポーリングを止め**、切れたら（`error`）、1.5 秒のポーリングに戻す。**つながっていたものが切れた 1 回だけ**、すぐ全体を取り直す（「サーバーに接続できません」を、すぐ出すため）。**ポーリングは、削除せず、保険として残す**。通知で起きた取り直しが失敗したら、つながっていても、ポーリングに戻り、成功すれば止まる。
- (5) **CLI は、変えない**。`rikai stop`・全トピックが閉じたときは、プロセスの終了で、接続も閉じる。**N1（127.0.0.1 のみ）・N2（認証）に、影響しない**（既存の検査を、そのまま通る）。**対象外**：WebSocket・データを、通知に載せること。**既知の制約**：半開きの接続は、切れたことに気づけない（ping はコメント行で、画面から見えない。その間は、更新が止まる）・ワーカーの `EventSource` が 403・503 で閉じられたら、全タブを閉じてワーカーが終わるまで、つなぎ直さない（その間は、ポーリング）・サーバーを本物に再起動すると、起動のたびに、ポートと合言葉が変わるため、画面は 403 になり、開き直しが必要（従来どおり）

### F39 いま誰の番かが一目で分かる

> 後続の変更：F47（[小さな UI の直し](ui-cleanup.md#f47-小さな-ui-の直し)）・F48（[名前と状態の言葉と上のバーの整理](ui-cleanup.md#f48-名前と状態の言葉と上のバーの整理)）が、この機能の該当の部分を置き換える。

**「いま、誰の番か」が、一目で分かる**（利用者の依頼：2026-11-23。「submit 待ち状態か？どれに対して Submit 待ちかが、ぱっと見わからない。何か解決方法ないかな？」→ 案 1〜4 を示し、「案４まで進めて」。背景：それまでは、Submit 済みで AI が未処理のとき〔「AIの返信待ち」〕だけ印が出て、AI が返信して「あなたの番」になったときの印がなかった）：

- (1) **状態の判定は、`lib/turn.ts` の 1 か所**（純粋関数。上から優先）：**closed**（既存の「終了」）→ **unsent**（未送信が 1 件以上。開いているトピックだけ：「未送信 n 件 → Submit」。琥珀。Submit に輪）→ **waiting-ai**（`pending > 0`：「AIの返信待ち」。灰色。コピーのボタンとヒントは残す）→ **empty**（スレッド 0：印なし）→ **your-turn**（**AI の新着返信か、未回答の質問がある**：「あなたの番 n」。青）→ **open**（未解決のスレッドだけが残っている。新着も未回答の質問もない：「未解決 n」。**灰色の中立な印**。`CircleDot`）→ **done**（スレッドが 1 つ以上で、すべて解決：「すべて解決」。緑）。**数え方**：AI の返信＝`ui.seen` にない AI の発言／未回答の質問＝AI の ask のうち、回答がなく、スレッドが未解決で、会話が先へ進んでいないもの。**解決済みスレッドの返信と質問・答えないまま会話が進んだ質問〔stale〕は、数えない**。**見える数字と、タイトルの `(n)` は、「新着の AI の返信か、未回答の質問を持つスレッドの数」**（`Turn.mine`。返信 1 通に質問が付いていても 1）。内訳（AI の返信 n・未回答の質問 m。項目の数。0 の項目は出さない）は、ボタンの `title`・`aria-label` に出す。**他のトピック**（開いていない）は、要約（`pending`・`progress`・`closed`）だけで判定する：未回答の ask（`asks.total − answered > 0`）があれば「あなたの番」・なければ未解決で「未解決 n」（灰色）。未送信と、AI の新着返信は、要約から分からないので、出さない。接続できない・サーバーのエラーのときは、`#turn` を出さず、警告を先に出す。
- (2) **上のバー（案 1）**：`#turn`（`role="status"`・`aria-live="polite"`。見える文字は `aria-hidden`。**読み上げ用の `.turn-sr` は、件数を含まない状態名だけ**：「あなたの番」「未送信あり」「AIの返信待ち」「すべて解決」「未解決あり」〔件数が変わるたびに、読み上げ直さない。件数は `aria-live` の外〕。押せる状態は、ボタンの名前に内訳と説明）。表示は短く（「あなたの番 2」）。900px 以下で内訳を、560px 以下で文字を隠し、アイコンだけ。**幅が足りないときは、進み具合のチップと「Claude Code 以外は…」のヒントを、先に縮め（省略記号つき）、`#turn` は縮めない**（Submit と重ならない）。Submit 済みで、新しいコメントを付けると、未送信が先に出る（前回分の「AIの返信待ち」は、小さな札で残す）。**押すと移動**：あなたの番 → AI の新着返信のあるカード → 未回答の質問のカード → 最初の未解決のカード／未解決 → 最初の未解決のカード（解決済みタブ・1 枚表示は解く。他のページのスレッドなら、そのページへ移ってから選ぶ）／未送信 → Submit にフォーカス。
- (3) **左の一覧（案 2）**：印は、**どの幅でも、アイコンだけ**（名前は `title`・`aria-label`）：あなたの番＝アイコン・未送信＝`Send`・未解決＝`CircleDot`（灰色）・すべて解決＝`CircleCheck`。**例外：「待ち」は、従来どおり文字つき**。現在のトピックは `#turn` と同じ判定。
- (4) **カード（案 3）**：札：「回答待ち」青・「AIの返信」青・「AIの返信待ち」灰（`meta.pending` の round）・「未送信」・「解決済み」。AI の新着返信と未回答の質問が重なるときは、「回答待ち」の 1 つにまとめる。
- (5) **タブのタイトル（案 4）**：`(n) あなたの番 | 題 | rikai`・`未解決 n | 題 | rikai`・`AIの返信待ち | …`・`未送信 n 件 | …`・`すべて解決 | …`・状態なしは `題 | rikai`（`n` は、(1) の数）。題は 40 字に切る（**コードポイント単位**。絵文字が割れない。`lib/dom.ts` の `trunc` 全体）。`document.title` に文字のまま入れる（HTML としては解釈されない）。更新は `App.tsx` の 1 か所。
- (6) **サーバー・CLI・HTTP・データの形式は、変えない**（画面が持つデータだけ）。**対象外**：ブラウザの通知・音・**AI が `poll` で待っているかの表示**（サーバーから分からない）。**既知の制約**：**ほかのトピックの印が、開いた瞬間に変わることがある**（一覧の API が、未送信の数を返さないので、別のトピックの未送信は、一覧では「あなたの番」〔未回答の質問があるとき〕に見え、開くと「未送信」に変わる。Submit を忘れやすい。将来は `/api/topics` に `unsent` を足す）・**Submit 済みの間は、別のスレッドの未読の AI 発言があっても、「AIの返信待ち」だけが出る**（設計どおり）・**AI の新着返信は、一覧の API から分からない**ので、ほかのトピックの「あなたの番」は、未回答の質問があるときだけ判定できる・「見た」の記録は、ブラウザごと（`localStorage`）・左の一覧は、「待ち」の文字が付くとき、題が少し短く切れる・上のバーが 400px 前後のとき、進み具合のチップ（「解決 n/m」）は、従来どおり切れる（`#turn` は、アイコンだけで収まる）・あなたの番のうち、AI の新着返信は、カードを開くたびに「見た」になるため、押してから戻ると、次の項目へ進む

### F41 確認すべきイベントをブラウザの通知で知らせる

**確認すべきイベントが起きたら、ブラウザの通知で知らせる**（利用者の依頼：2026-11-23。「資料の更新・AI の返信など、確認すべきイベントが起きたら、Web プッシュか Mac の通知で知らせてほしい」→ **全 OS 共通のブラウザの通知（`Notification` API）**を選択。**Web Push は、ブラウザの会社の Push サービス〔外部〕を経由するので、N1〔通信は 127.0.0.1 だけ〕に反し、採らない。サーバーから OS の通知を出す案**〔macOS は `osascript`・Linux は `notify-send`・Windows は PowerShell〕**は、OS ごとの実装になり、Linux・Windows は確かめられないので、見送った：のちに、不要と決まった〔利用者の決定：2026-11-24〕**。画面が SSE〔F38〕で更新を受けたとき、画面を見ていなければ、ブラウザが OS の通知を出す。**0.23.1：通知に、アイコン画像を付けた**〔利用者の依頼：2026-11-23。「通知時にアイコン画像も表示してほしい」〕。**0.27.0：通知の対象を、すべてのトピックに広げた**〔F46〕）：

- (1) **ベル**：上のバーに、**アイコン 1 つのボタン**（`NotifyBell`。外観ボタンの左。`Bell`〔オフ〕・`BellRing`〔オン。アクセント色〕・`BellOff`〔押せない〕）。押すとオン／オフ。**既定はオフ**。オンにする操作で、`requestPermission()` を求める（Promise 形式とコールバック形式の両方に対応）。拒否ならオフのまま。`Notification` がない・許可が `denied` のときは、押せず、理由を `title`・`aria-label` に出す。設定は `localStorage` の `rikai-ui` の `notify`（外観の切り替えと同じ流儀。壊れた値は既定のオフに戻り、ほかの設定は保たれる）。**保存がオンでも、許可が `granted` でなければ、オフ扱い**。許可・保存は、**オリジン〔ポート〕ごと**：サーバーを起動し直すとポートが変わるので、ベルはオフに戻り、許可を求め直す（想定内の制約）。
- (2) **出す条件**（`lib/notify.ts` の `shouldNotify`。純関数）：**ベルがオン・許可が `granted`・画面を見ていない**（`visibilityState !== 'visible'` か `!hasFocus()`）・**前回から、新着がある**。
- (3) **新着は、ID の比較で決める**（件数の差ではない：件数の差では、読んだあとに来た返信を洩らす〔独立レビューの Major〕・解決の取り消しで誤って出す、ため）：前回までに知っていた、AI の発言の ID の集合〔返信＝質問のない AI の発言・質問付きの AI の発言・そのうち未回答のもの〕と、ページごとの版のキー（`ページ@版`）を持ち、**前回の集合に無い ID**を新着とする。質問は、前回の質問の集合に無く、**いま未回答**のもの（`awaitsAnswer`。0.27.0 から `shared/fresh.ts`。F39 の判定は変えない）。**読んだこと・解決の取り消し・自分のメッセージの削除・質問への回答や取り消し・ID が縮むだけでは、出ない**。**質問付きの 1 通は、「質問 1」だけ**（返信には数えない）。**最初の取得・つながり直し（`ui.live`）の直後・トピックを開き直したときは、ベースライン**（通知しない）。**対象は、すべてのトピック**（0.27.0〔F46〕から。**開いているトピック**：取得した全体の ID の集合から。**ほかのトピック**：一覧の API の `fresh` の、前回との差から。0.26.x までは、開いているトピックだけだった）。
- (4) **累計**：画面を見ていない間に溜まった新着の合計を出す（トピックごと。1 回目「返信 1」→ 2 回目「返信 2」。`tag` が同じなので、置き換わる）。画面が見える状態に戻ったら 0。
- (5) **内容**：タイトル「rikai」・本文「（トピック名）：AI から返信が届きました（返信 2・新しい版 1・質問 1）」（0 の項目は省く。**版だけのときは、「資料が更新されました（新しい版 n）」**）。トピック名は 40 コードポイントで切る（絵文字を割らない。**制御文字と、双方向文字の制御を除く**）。**`icon` は、rikai の PNG の `data:` だけ**（`lib/notifyIcon.ts` の `NOTIFY_ICON`：`public/favicon.svg` を 192px で描いた PNG。2,942 バイト・RGBA・角は透明。**通知のアイコンは、多くのブラウザで SVG が使えないので、PNG の `data:` にした**。外のものを読まない・サーバーへの通信は増えない：N1）。**`favicon.svg` の SHA-256 を `NOTIFY_ICON_SOURCE_SHA256` で持ち、単体テストが、favicon の変更で落ちる**（アイコンの作り直しを促す）。**`badge`・`data` は付けない**。`tag` は `rikai-<slug>`。**AI の本文・資料の中身は載せない**（N6）。
- (6) **押すと**：`window.focus()`・通知を閉じる・そのトピックを見ていれば F39 の `goToTurn`（最初の新着）・別のトピックなら、そのトピックを開く。
- (7) **複数のタブ**：同じ `tag` で、OS の通知が置き換わる（実 Chrome で確認：2 タブで同時に出すと、先のものが閉じられ、残るのは 1 つ）。
- (8) **N1〜N3**：通信は増えない・`innerHTML` を使わない・外のものを読まない。サーバー・CLI・HTTP・データの形式は、0.26.x まで変えていない（**0.27.0 で、`/api/topics` に、省略できる `fresh` を足した：F46。`.rikai/` の保存の形は、変えない**）。**対象外**：音・タブを閉じていても届く通知・Web Push・サーバーからの OS 通知（不要と決まった：§7）。**既知の制約**：OS の通知を押しても、ブラウザが前面に来ない場合がある（`window.focus()` は、ブラウザ・OS の判断による）・`hasFocus()` が常に false を返す環境では、通知が出続ける（Tern などで、未確認）・許可・保存は、ポートごと（起動し直すと、許可を求め直す）・「見た」の記録（F39）と同じく、ブラウザごと・**OS の通知センターで、アイコンが実際に表示されるかは、未確認**。**ほかのトピックについての制約は、F46 の行を見る**

### F46 ほかのトピックの新着も通知する

**ほかのトピックの新着も、ブラウザの通知で知らせる**（利用者の決定：2026-11-24。`html-app-review`。F41 の「開いているトピックだけ」を広げる。0.27.0）：

- (1) **サーバー**：`GET /api/topics` の、トピックごとの項目に、省略できる **`fresh`**：`{ replies: string[]; asks: string[]; openAsks: string[]; versions: string[]; window?: number }`（`shared/fresh.ts` の `freshOf`：F41 の `snapshotOf` が使うのと、同じ種類の ID。`replies`＝質問のない AI の発言・`asks`＝質問付きの AI の発言・`openAsks`＝そのうち未回答・`versions`＝`ページ@版`）。**サーバーと画面が、同じ関数を使う**（開いているトピックの `snapshotOf` も、同じ `freshOf` を、上限なしで呼ぶ）。**上限（窓）**：各項目は、**新しい側〔ID の連番が大きい側〕から、窓の大きさ個**。**窓は、通知の対象〔閉じていない・読める形式〕のトピックの数 N で割る**：**`freshWindow(N) = clamp(floor(4000 / N), 20, 200)`**（N = 1・5・20・21・40・100・200・201・1000 で、200・200・200・190・100・40・20・20・20）。**対象の全トピックに、同じ大きさの窓で `fresh` を付ける**（0.27.0 の最初の形は、「応答全体で ID 合計 4000 個を超えたトピックには付けない」で、20 トピック × 各 200 件で、一覧の順で後ろのトピックに付かず、何が来ても通知されなかった：独立レビューの Minor。直した）。**窓の大きさは、`fresh.window` として、応答に含める**（省略できる。上限なしで作った `fresh` には付かない）。**窓は、各項目の上限で、1 トピックに最大 4 項目あるので、ID の合計は、最大で約 4 倍〔最悪 16000 個〕**。**対象が 200 を超えるとき**だけ、予算を超える：`meta.json` の更新が新しい順に 200 個に `fresh` を付ける（窓は 20）。それでも外れるトピックは、ありうる。**`openAsks` は、切ったあとの `asks` の部分集合**（窓の外の古い質問が、毎回「新着」に見えないように）・**閉じたトピックには付けない**。**計算**：`store.summaryOrNull(meta, 窓)` が、`progress` と `fresh` を、`threads.json` の 1 回の走査で作り、結果を、`rev`・更新時刻・大きさ・**窓**をキーに、覚える（変更のないトピックは、読み直さない。手で書き換えたファイルも、検出する。窓が違えば、別の結果）。**`.rikai/` の保存の形は、変えない**。API の応答に、省略できる項目を足すだけ（古い画面は、無視できる）。`answerOf`・`askStale`・`awaitsAnswer` を、`panel/logic.ts`・`lib/turn.ts` から、`shared/fresh.ts` に移した（呼び出し側を付け替え）。
- (2) **画面**（`useBrowserNotify`）：**開いているトピック以外**を、一覧の `fresh` の、前回との差（ID の比較）で通知する（SSE の `changed` で、一覧が取り直される経路）。**開いているトピックは、これまでどおり**、取得結果から作る、全体の ID の集合で通知する（**二重に通知しない**：開いているかは、トピックのクエリを見ているか〔observer がいるか〕で決める。一覧の経路は、開いているトピックを見ない）。前回の状態は、両方の経路で共有する `last` に、**取得元（トピックか一覧か）つき**で持つ。
- (3) **ベースライン**（通知を出さず、基準だけ取る）：最初の一覧・`ui.live` の直後・一覧に新しく現れたトピック・**取得元が、一覧からトピックに変わったとき**（開いたとき：一覧の `fresh` は、新しい側の窓だけなので、全体とは、直接、比べない）・**`fresh.window` が、前回より大きくなったとき**（古い ID が、窓に新しく入っても、新着に見えないように。窓が縮むときは、古い ID が窓から消えるだけなので、そのまま比べる）。閉じたトピックは、記憶も消す。
- (4) **件数**：新着が、窓の大きさに達した項目には、**`capped`** を付け、通知は「返信 200 以上」のように出す（累計しても、「以上」は残る。開いているトピックは、上限がないので、付かない）。**変えていない点**：累計（トピックごと）・画面を見ていないときだけ・`tag`（`rikai-<slug>`）・内容（トピック名と件数だけ：AI の文章・資料の中身は載せない）・押すと、そのトピックを開く・ベルと許可は F41 のまま（`shouldNotify`・`notifyBody`・`showNotification` を再利用）・通信は増えない。**SKILL.md は、変更なし**（AI への指示は、変わらない）。
- (5) **`styles` の値の上限**：`STYLE_VALUE_MAX` を、**80 → 300 文字**にした（利用者の決定：2026-11-24。F42・F45）。許可リスト・キー数・`text` 80・`selector` 200・`frameMeta` 全体 16KB は、変えない。301 字以上：橋は、300 字に切って送るので、正規の経路では、`pick` は捨てられない／枠が、301 字以上を、そのまま送った偽物は、`parsePick` が、`pick` ごと捨てる（今までどおり）。**既知の制約・判断**：名前は `fresh`・**開き直した直後は、開く直前に届いた返信を、通知しない**（開いた時点で、画面に見えているため）・**1 回に、窓の大きさ以上の新着が届くと、件数は「N 以上」まで**・**対象のトピックが 200 を超えると、更新の古いトピックは、通知されない**・**窓が広がった瞬間に届いた新着は、ベースラインに吸収され、通知されない**（窓が変わるのは、トピックの増減のときだけ）・**新しいページは、「新しい版」として数える**（F41 の数え方のまま）・トピックを消しても、サーバーの `summaries` と、画面の `last` の記録が残る（トピックの数だけで、小さい）・F39 の「あなたの番」は、変えていない（`fresh` は、通知にだけ使う）・実際のマウス・他ブラウザ・OS の通知センターは、未確認
