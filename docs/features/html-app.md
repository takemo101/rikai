### F28 資料に実行できる枠 html-app を書ける

**資料に、JavaScript で動く部品（実行できる枠）を書ける**（利用者の判断：2026-11-22。2026-11-21 の「入れない」を変更。スライダー・計算機・状態遷移のデモなど、触って理解する資料のため）：資料（本文）に ```` ```html-app ````（情報文字列に `height=480`〔120〜1200px の固定。なし・`height=auto` は自動の高さ：F40〕）のコードブロックを書くと、その中身（HTML・CSS・JavaScript。自己完結）が、**隔離した枠（iframe）の中で動く**。**画面と枠の、狭い通信路（橋）は、F40（高さの報告・外観の受け渡し）と F42（要素を選んでコメント・状態の添付・枠の画像）。「枠は、親に触れない」の例外は、この橋のメッセージだけ**（親が、`e.source`・形・大きさ・頻度を検査して、下書き・範囲の画像にだけ使う）。**隔離**：

- (1) 枠の iframe は、`sandbox="allow-scripts"` だけ（`allow-same-origin` を付けない：オリジンのない文書になり、画面の DOM・Cookie・合言葉・localStorage に、触れない。ポップアップ・上の画面の移動・フォームの送信・ダウンロードも、できない）。`allow` は空。
- (2) 枠の中身は、画面とは**別の文書**として、`GET /appframe/<topic>/<page>/<版>/<n>`（合言葉・`Host`・`Origin` の検査つき）で配る。**サーバーが、同じ版の資料から、n 番目のフェンスを取り出す**（ブラウザが送った中身は、使わない。数え方は、同梱の marked の字句解析と同じ：文書の順・箇条書きや引用の中も）。取り出しは、**別のスレッドで、3 秒で切る**（AI が書いた資料は非信頼で、入れ子の箇条書きなどで、解析が、とても遅くなる・メモリを使う〔実測：800 段で 1.3 秒、1200 段で 4.4 秒〕。時間切れ・メモリ超過（256MB）・解析の例外は 422。資料は 4MB まで、超えると 413。結果は版ごとに覚え、**失敗も 60 秒覚える**。同じ資料の進行中の解析は共有し、worker は同時に 2 つまで）。
- (3) その文書の CSP：`sandbox allow-scripts; default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:; font-src data:; media-src 'none'; connect-src 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'self'`。`X-DNS-Prefetch-Control: off`。**外への通信は、WebRTC を除いて、すべて止まる**（fetch・XHR・WebSocket・画像・外のスクリプト／CSS／フォント・iframe・ワーカー・移動）。`eval` は使えない。
- (4) 画面（index.html）の CSP は、`frame-src http://<host>/appframe/` だけを足す（同じサーバーの、ほかの URL〔/api・/asset など〕は、枠にできない）。**止められないもの（既知の限界）**：**WebRTC**（STUN・TURN への通信。CSP の対象でなく、`webrtc` ディレクティブは Chrome 150 で効かない〔実測〕。枠の中に `srcdoc` の iframe を作ると、子の文書が、新しい realm で、元の `RTCPeerConnection` を持つ〔`frame-src` は `about:srcdoc` を止めない。実測：待ち受けに UDP が届いた〕。直接呼ぶ道だけを塞ぐ補助は、迂回できるので、置かない）・DNS の先読みの一部・無限ループによる画面の固まり。枠の中には、画面の秘密は渡らない。ただし、**利用者が枠に入力した文字は、外へ出せる**ので、枠の見出しの行の `title`・`aria-label`（読み上げ・ホバー。**見える文字では出さない**：0.1.6〔F56〕。比べる画面は iframe の `title`）で、「パスワードなどの秘密は、入力しないでください」と伝え、SKILL.md で、AI に、秘密を求めないよう伝える。**対象は、資料の本文だけ**（AI の返信・前の版の差分では、ふつうのコードブロック）。1 つの中身は、200KB まで（超えると 413）。**「ソースを見る」**（折りたたみ。文字として。ソースは、描画の表から付け、資料の生の HTML の `data-src` は、使わない）で、利用者が、動くものを読める。コメントは、**枠を 1 つのブロックとして**付ける（ソースから位置づけ・差分の文字を作る。枠の中の文字は、選べない。枠の上では、入口のバーが出ないので、見出しの「この枠にコメント」から。**枠の中の要素は、「要素を選んでコメント」から：F42**）。範囲の画像（F25）には、枠の中は、**枠自身が作った画像**が写る（F42。できなければ「枠の箱」）。**画面を描き直すと（コメントの追加など）、枠の中の状態は、最初に戻る**。**版を並べて比べる画面（F44）にも、枠は、読み取り専用で出る**（同じ隔離・同じ橋・同じ登録簿。枠ごとのツールバー・「この枠にコメント」・要素選択・個別表示は出さない。幅・外観は、比較用のツールバーで、左右そろえて変える。**枠の中の状態は、左右で共有しない**）

### F40 html-app の枠と画面をつなぐ橋

> 後続の変更：F48（[名前と状態の言葉と上のバーの整理](ui-cleanup.md#f48-名前と状態の言葉と上のバーの整理)）が、この機能の該当の部分を置き換える。

**html-app の枠が、画面と、狭い通信路（橋）でつながる**（段階 1：自動の高さ・配色の供給・幅と外観の切り替え。利用者の方針：2026-11-23。「html を強化していく。デザインの比較・UI のレビューにも使いたい」。rikai の `html-app-review` トピックで、利用者が質問に回答：**書き戻しは「下書きのコメントだけ」**〔自動で Submit しない〕・**枠の状態の添付は入れる**・**橋のあとは「要素を選んでコメント」を先に**・**`height=` を書かない枠は自動の高さ**・**幅の切り替えは 375・768・1280・1920px の 4 つ**・用途は「画面の比較・位置・ボタンのデザインのレビュー」。**書き戻し・状態の添付・要素を選んでコメントは、段階 2〔§7〕。この行は段階 1 だけ**）：

- (1) **自動の高さ**：情報文字列に `height=` がない・`height=auto` の枠は、**自動**（最初は 200px）。`height=N`（120〜1200）は**固定**（従来どおり。既存の資料は変わらない）。枠の中の橋のスクリプトが、`ResizeObserver`・読み込み・フォント・数回の遅延で、高さを測り、`parent.postMessage({__rikai:1, type:'resize', height}, '*')` で知らせる。**揺れ防止**（高さが A → B → A と往復して CPU を使い切る・`100vh` ＋余白の循環を止める）：報告は 250ms に 1 回まで・測りは 50ms に 1 回まで・1 秒以内の往復が 2 回続いたら、大きい方に留まる。**`100vh` ＋余白のように、増え方が同じ循環は、2 回で検出し、最後に測った高さ（大きい側）を 1 回報告して止める。止めたあと、超える分が 64px 以下で、報告する高さが 2400px 以下のときだけ、枠の中を `overflow-y: hidden` にし、それ以外は `auto`（枠の中をスクロールできる）にする**（違う変化が来たら解く。`min-height: 100vh` の下に、本物の節が続く資料〔ランディングページのモックなど〕の中身を、隠さないため。`hidden` のとき、余白の数 px が切れることがある）。画面の受け口は、**ドキュメントで 1 つ**（枠が 0 になったら外す）。**検査**：`e.source` が、画面が置いた枠の `contentWindow` のどれか（sandbox の枠は、オリジンが `null` で、オリジンでは検査できないので、送り元の窓で）・形が厳密（`{__rikai:1, type:'resize', height:number}`）・有限で正の数だけ・整数に丸め・**120〜2400px に収める**（NaN・無限・負・0・型違いは捨てる）・**その枠だけ**を変える（1 つの枠が、別の枠の高さを変えられない）・固定の枠は無視・`requestAnimationFrame` でまとめる・**1 つの枠につき 1 秒に 6 回まで**。
- (2) **配色の供給は、オプトイン**：**中身が、画面の配色への対応を示している枠だけ**に、土台のスタイルと、ダークへの追従を付ける。**対応の印**（`shared/htmlapp-theme.ts` の `followsTheme(content)`。サーバーと画面で同じ関数）：**(a) 橋が配る色の変数を使い、同じ名前を自分では定義していない**：`var(--color-<名前>`（直後が `)`・`,`・空白）を使っていて、`--color-<名前>:` の定義がない。**名前は、`BRIDGE_COLORS`（橋が配る色：`bg`・`surface`・`ink`・`ink-2`・`muted`・`line`・`accent`・`accent-ink`・`accent-fill`・`ok`・`warn`・`err`）。土台のスタイルの `:root` の宣言も、判定の名前も、同じ表から作る**。`--color-primary` のような、橋が配らない名前は、印ではない（自分で `--color-*` を作る資料は、AI がよく書く形：土台を付けると、背景だけが残り、ダークで、文字が白くなる）。名前の前方一致は取り違えない（`--color-ink` と `--color-ink-2`・`--color-inks`）。**(b) `<meta name="color-scheme">`**（標準の、明示の宣言）。**`data-theme` という文字は、印にしない**（本文に書いただけで true になるため）。単純な文字の検査なので、コメント・文字列の中の `var(--color-bg)` も、使っているとみなす（まれ。土台が付いて、ダークに従う：許容。害は、ゼロではない）。**true の枠**：`<html data-follow data-theme>`・土台のスタイル（**すべて `:where()`＝詳細度 0**：AI の CSS が、つねに勝つ）・ダークへの追従。CSS 変数（ライト・ダーク）：`--color-bg`・`--color-surface`・`--color-ink`・`--color-ink-2`・`--color-muted`・`--color-line`・`--color-accent`（線・アイコン）・`--color-accent-ink`（文字・リンク）・`--color-accent-fill`（白い文字を載せる塗り）・`--color-ok`・`--color-warn`・`--color-err`・`--font-sans`・`--font-mono`・`--radius`。`body`・`button`・`input`・`select`・`textarea` の控えめな既定（`box-sizing: border-box`）。**false の枠（従来の資料）**：文書は `<!doctype html>\n<meta charset="utf-8">\n<script>橋</script>\n中身` だけ（従来との差分は、橋の `<script>` だけ。単体テストで固定）・**常にライト**（地は、ライトは白・ダークは黒〔`iframe[data-mode]`〕）・画面の外観が変わっても、何も送らない。従来の資料の見た目（何も書かない・背景だけ・body だけ・全部書いた、をライト・ダークで）は、橋なしの単独ページと、計算済みのスタイルが完全一致・位置 1px 以内・画素の違い 3% 未満（実測）。`/appframe/…?mode=light|dark`（**`light` か `dark` が、ちょうど 1 つのときだけ有効**。それ以外は、指定なし）で、`<html data-theme>` を付ける。**画面の外観が変わると、親が `{__rikai:1, type:'theme', mode, by:'auto'}` を枠へ送る**（再読み込みなし。枠の中の状態を失わない）：`by: 'auto'`（画面の外観の変化）は、**`data-follow` の枠だけ**に効く。`by: 'user'`（ツールバーの操作）は、**どの枠でも**効く。枠の側は、`e.source === parent`・`mode` が 2 値のどちらか・`by` を確かめる。**「ダークでも、枠は常にライト」（F36 (8)）は、オプトインした枠だけ、「画面の外観に従う」に変わった**（従来の資料は、従来どおり、常にライト）。
- (3) **見出しの行（`.cap`）のツールバー**（アイコンだけ・`aria-label`・`title`・テキストなし。`flex-wrap: wrap`：狭い窓でも、はみ出さない）：**幅**（`Smartphone` 375・`Tablet` 768・`Monitor` 1280・`Tv` 1920・`ArrowLeftRight` 自動）：**選んだ幅で、枠のレイアウトを計算する**（iframe の実際の幅が、選んだ幅：枠の中の `@media`・`vw`・`100%` は、その幅で効く）。**選んだ幅が本文より広いときだけ、縮小して見せる**：縮小率 `s = max(0.5, 本文の幅 ÷ 選んだ幅)`（**下限 50%**。1920px を、本文 634px で 33% にすると、読めないため）。**50% でも、本文の幅に収まらないときは、枠の置き場が、横にスクロールする**（`title`：「枠の幅：デスクトップ（1280px・表示は 50% に縮小）」「…表示は 50% に縮小。横にスクロールできます」）。**構造は 3 層**：`.appview`（本文の幅の箱。横にスクロール）> `.appscale`（縮小後の幅・高さの箱。はみ出す分を切る。高さ＝枠の高さ × `s`）> iframe（`transform: scale(s)`・`transform-origin: top left`）。`transform: scale` は、スクロールできる範囲を、縮小前の幅のままにするため、`.appscale` を挟む。枠の線は、横スクロール時の内側の輪（`outline-offset: -2px`）。自動と、本文以下の幅は、縮小しない。`ResizeObserver` で、窓・パネル・左の一覧の開閉に追従する。縮小した枠でも、マウス・キーボード・ホイールは、正しく届く。**枠だけのライト／ダーク**（`Sun`／`Moon`。`by: 'user'`）。保存しない（同じ版の中で、本文を描き直すあいだは、メモリで覚える。画面の外観が変わると、枠だけの外観は、画面の外観に戻る）。
- (4) **変えないもの（安全）**：**`APP_CSP` は変えない**（`sandbox allow-scripts`・`connect-src 'none'` ほか）・iframe は `sandbox="allow-scripts"` だけ・`allow-same-origin` なし・外部通信なし。**画面と枠のあいだの通信は、高さの報告（枠 → 画面）と、外観（画面 → 枠）の 2 種類だけ**で、画面の DOM・コメント・保存には触れない（N3 の例外の説明に、この 2 種類を足した。N3 の本質は変えない）。**対象外**：書き戻し（枠からコメント・状態を送ること）・要素を選んでコメント・前の版と並べて比べること・枠の横並び・返信の中の枠（段階 2・3。§7）・デスクトップの幅そのものでの表示（本文の外へはみ出させる案：入れていない。縮小表示で代える）。**既知の制約**：枠の線を `border` → `box-shadow` に変えたため、従来の枠の中身が、2px 広く・高く描かれる（幅の境目で、ぎりぎり折り返す資料は、折り返しが変わりうる）・画面の外にある枠は、縮むのが遅れる（Chrome が、画面外の別オリジンの枠で `ResizeObserver` を止める。見える所へスクロールすると、約 300ms で直る）・縮小した枠の横スクロールは、macOS のオーバーレイのスクロールバーでは、スクロールするまで見えない（`title` で伝える）・枠が動いた直後に、押したことが枠に届かないことがある・`height=120.5` は、固定の 120（`\b`）・従来の資料を「枠だけダーク」にすると、文字色を書いていないものは、白い文字・黒い地になる（利用者が選んだ結果）・`100vh` ＋余白の止め方は、`hidden` のとき、余白の数 px が切れることがある・`.cap` が、狭いと 2 行になる・本文を描き直すと、枠の中の状態（カウンタなど）は失われる（従来どおり）

### F42 html-app の枠から下書きのコメントを作れる
